## walkthrough is a separate layer, not a sddio mode

- `walkthrough/` records what the product is for; `.sddio/` records what the code cannot say about
  itself. Neither reads the other's files, config, or vocabulary: no shared IDs, no relative links.
- The vocabulary is deliberately different — JOURNEY, STEP, STORY, MARKER, REFUSAL — because a shared
  name pulls both sides into copying each other's semantics.
- Every path written inside `walkthrough/` stays inside it. Its `AGENTS.md` names `rules/`,
  `journey.md`, `tech.md`, `specs/` and `decisions/`, and nothing above the folder.
- The one edge is a hook, declared in `config.json` and called by neither side: `knowledge.reconcile`
  fires when a card closes, not when a journey changes.

### Alternatives

- Add product artifact types to `sddio_docs/` — the admission test "the repository cannot say this" is
  meaningless for a claim about what a person should feel, and every added type weakens the rule that
  keeps sddio small.
- A second tree reusing SPEC, ADR, DISCUSSION — `specs/` beside `SPEC` is exactly the collision that
  makes two readers guess which one is binding.
- No folder at all, prose in a board card — the card is deleted at close, so a product direction kept
  there has a scheduled death.

### Consequences

- One repository holds two context systems; a session reads one and says which.
- The folder can be copied into a consumer unchanged, which is what ADR-002 does with it.
- sddio's `knowledge.reconcile` hook does not fire on walkthrough edits until someone asks it to.
- Not in the code: nothing reads `journey.md` yet. Until the compile verb exists, the separation is a
  rule about paths, held by review and by the suite in `walkthrough/specs/`.
