# Writing

Load this when an entry is about to be created or changed. Everything else is in
`instructions.md`, and reading it twice a session buys nothing.

## Admission

An entry is written only for a fact that reading the implementation cannot give you.

- Answer one line in the entry: `- Not in the code: <why the repository does not say this>`.
- If that line cannot be written, there is no entry. Not a shorter one — none.
- A fact the code or a shipped instruction already states is a citation: point at it with `refs`.
- A fact that can be regenerated by reading one file is not knowledge; it is a second copy that drifts.
- History is admissible: what was tried, what failed, who asked, and by when.

## Artifact roles

- `SPEC` — confirmed requirements. A command could falsify them.
- `ADR` — important technical decisions, the option that lost, and what each cost.
- `DISCUSSION` — unresolved knowledge; promoted into `SPEC` or `ADR`, then deleted.

Keep these roles distinct. Requirement or decision is settled by falsifiability: if a command could
fail, it is a `SPEC`; if only a person can be told why, it is an `ADR`.

## Classification

```text
Requirement   → SPEC
Decision      → ADR
Uncertainty   → DISCUSSION
Transient     → nothing
```

If several apply, create only the artifacts that are necessary.

## Entry style

1. One idea per line.
2. Bullets over paragraphs.
3. Keep lines under ~100 characters.
4. Facts only — no background, motivation, or history.
5. No filler: "clearly", "simply", "note that", "it is important".
6. Do not restate the title in the first bullet.
7. Reference other artifacts by ID; never repeat their content.
8. One level of nesting at most.
9. Omit a section that has nothing to say.
10. If a bullet needs two sentences, it is two bullets.

Shape test: every line is readable and actionable on its own.

## General rules

- Do not invent requirements.
- Do not create artifacts for completeness.
- Do not duplicate existing knowledge.
- Do not rewrite accurate artifacts.
- Do not record transient implementation details.
- Write every entry body in Entry style.
- A rule that can be checked names the command that checks it; a rule that cannot says it is judgement.
- Write a fact where it is read, and nowhere else.
- Prefer automatic, minimal, reversible actions.
- When intent cannot be determined safely, use `DISCUSSION`.

## Restraint

- Do the least necessary.
- Add structure only when it provides clear value.
- Prefer the smaller solution when multiple solutions work.
- A rule is removed when it is measured as unfollowed, not when it feels unfollowed.
- Apply the last rule to the last three reconciled ranges; measure with the `grep` the rule names.
